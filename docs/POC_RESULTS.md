# LLM 처리 방식 PoC 결과

> 모델: 로컬 7B급 LLM  
> 목적: 문서 유형별로 "안건/액션아이템 구조화" 추출 방식을 비교해 최적 전략 도출

※ 본 문서는 방법론과 성능 지표만 담습니다. 실험에 쓰인 원본 문서(회의록·기술 스펙)는 사내 자료라 저장소에 포함하지 않으며, 아래 내용에서 실제 문장·고유명은 모두 일반화했습니다.

---

## 방식 개요

| | 방식 | 설명 | LLM 호출 수 |
|--|------|------|------------|
| A | 단일 프롬프트 | 전체 문서를 한 번에 투입 | 1회 |
| B | Map-Reduce | 발화 라벨링 → 그룹핑 → 세그먼트 요약 | 1 + 그룹 수 |
| C | 타임스탬프 청킹 | N블록 단위 분할 → 청크별 처리 → 병합 | 청크 수 |
| D | 멀티패스 | 안건 추출 → 안건별 집중 추출 | 1 + 안건 수 |

세그먼트는 `topic`(핵심 안건) / `peripheral`(잡담·부수 발화) / `procedural`(진행 절차 발언) 3종으로 분류.

---

## 문서 유형별 결과 (지표만)

실험은 성격이 다른 3종 문서로 진행:

- **문서 1 — 구조화 회의록** (요약본, 타임스탬프 없음, 약 3.9K자)
- **문서 2 — 원시 회의 전사체** (타임스탬프 21블록 포함, 약 3.4K자)
- **문서 3 — 기술 스펙 문서** (DDL + 메서드 시그니처 형태, 타임스탬프 없음, 약 3.3K자)

### 문서 1 — 구조화 회의록

| 방식 | 소요 | 세그먼트(topic/peri/proc) | 액션아이템 | 비고 |
|------|------|--------------------------|-----------|------|
| A 단일 | 112초 | 1 / 0 / 0 | 2 | 전체를 한 덩어리로 요약 |
| B Map-Reduce | 322초 | 1 / 0 / 0 | 4 | A보다 느림, 안건 통합됨 |
| C 청킹 | 156초 | 1 / 0 / 0 | 2 | — |
| D 멀티패스 | 1067초 | 4 / 1 / 0 | 13 | 유일하게 안건 분리 성공(잡담성 1건 포착), 그러나 18분 소요 |

→ 이미 섹션으로 정리된 문서라 A~C는 하나로 뭉개짐. D만 안건을 분리했으나 속도가 비실용적.

### 문서 2 — 원시 회의 전사체

| 방식 | 소요 | 세그먼트(topic/peri/proc) | 액션아이템 | 비고 |
|------|------|--------------------------|-----------|------|
| A 단일 | 253초 | 7 / 2 / 1 | 10 | **가장 균형** — 안건·잡담·절차 모두 포착 |
| B Map-Reduce | 1052초 | 3 / 3 / 0 | 8 | 17분 소요, 안건 과통합(서로 다른 안건이 한 세그로 뭉침) |
| C 청킹(재실행, 900s 한도) | 372초 | 22 / 3 / 8 | 20 | 과분리. 청크 1건 빈 응답 실패, 일부 청크 언어 혼용, 화자 이름이 세그 제목으로, 단순 동의 발화까지 procedural로 분리 |
| D 멀티패스(재실행, 900s 한도) | 663초 | 10 / 0 / 0 | 15 | 안건 정밀 분리(최다)나 잡담 완전 미포착, 날짜 할루시네이션, owner 다수 빈값, 원문에 있는 키워드 미검출, 일부 안건 요약 오염 |

### 문서 3 — 기술 스펙 문서

| 방식 | 소요 | 세그먼트 | 액션아이템 | 비고 |
|------|------|---------|-----------|------|
| A 단일 | 75초 | 1 / 0 / 0 | 2 | 전체를 1개로 뭉갬 |
| B Map-Reduce | — | — | — | ❌ JSON 파싱 오류 |
| C 청킹 | 732초 | 12 / 0 / 0 | 5 | 과도하게 12개로 쪼갬 + 빈 제목 세그 다수 발생 |
| D 멀티패스 | — | — | — | ❌ 타임아웃 |

→ 3스트림(topic/peri/proc) 분류 자체가 기술 문서에 부적합.

### 4방식 전체 비교 (원시 전사체 기준)

| | A 단일 | B Map-Reduce | C 청킹 | D 멀티패스 |
|--|--------|-------------|--------|-----------|
| 소요 | **253초** | 1052초 | 372초 | 663초 |
| 세그먼트 수 | 10개 | 6개 | 33개 | 10개 |
| peripheral 포착 | ✅ 2건 | ✅ 3건 | ✅ 3건 | ❌ 0건 |
| owner 정확도 | 중 | 중 | 중 | 낮음 (빈값/할루시) |
| 언어 일관성 | ✅ | ✅ | ❌ 영어혼용 | ✅ |
| 안건 분리 정밀도 | 중 | 낮음(과통합) | 낮음(과분리) | **높음** |
| 오류 없음 | ✅ | ✅ | ⚠️ 청크실패1 | ⚠️ 키워드오류 |

### 핵심 발견

**1. 원시 전사체 → 방식 A가 최적**
- 가장 빠르고(253초) 세그먼트 품질도 가장 좋음(10개, 잡담성 발화 2건까지 정확 포착)
- B는 17분이나 걸리고 서로 다른 안건이 하나로 과통합됨
- C/D는 전사체에서 과분리·오류·미포착 발생

**2. 타임스탬프 유무가 방식 선택의 핵심 변수**
- 타임스탬프 있는 문서(전사체): A가 압도적
- 타임스탬프 없는 구조화 문서(요약본): A~C 모두 하나로 뭉개짐, D만 안건 분리

**3. 기술 문서에 3스트림이 맞지 않음**
- A는 1개로 뭉개짐, C는 과도하게 쪼개짐 + 빈 제목 발생
- 기술 문서 → 3스트림이 아니라 **헤딩(## 단위) 파싱**이 적절

**4. 방식 B(Map-Reduce)의 실제 문제**
- 배치 라벨링은 빠르지만 각 그룹 요약 호출이 직렬로 쌓여 총 시간이 오히려 A보다 4배 느림
- 타임스탬프 없으면 단락 단위 fallback → 불안정한 라벨링

**5. 방식 D(멀티패스)는 이미 구조화된 문서에만 유효**
- 구조화 회의록에서 유일하게 안건별 분리 성공
- 하지만 18분 소요 → 실시간 처리 불가

### 결론: 문서 유형별 전략

| 문서 유형 | 최적 전략 | 이유 |
|---------|---------|------|
| **원시 전사체** (타임스탬프 포함) | **방식 A** (단일 프롬프트) | 빠르고 정확, 잡담성 발화까지 포착 |
| **구조화 회의록** (요약본 등) | **헤딩 파싱** (LLM 불필요) | 이미 섹션으로 분리됨 → 파싱만으로 충분 |
| **기술 문서** (스펙 문서) | **헤딩 파싱 + 필요시 A** | 3스트림 부적합, 섹션 단위 sub-doc화 |
| **긴 전사체** (32K자 초과) | **타임스탬프 청킹 + A 병렬** | 청크별 병렬 처리 (C의 직렬 타임아웃 문제 해결) |
