# GeryonMCP 초급 개발자 가이드

> **누구를 위한 글인가**: 검색 엔진·임베딩을 처음 접하는 주니어 개발자가, 이 코드베이스가 **무슨 일을 어떻게 하는지** 이해하고 직접 만져볼 수 있도록 쓴 설명서입니다. 어려운 용어는 그때그때 풀어 씁니다.

---

## 0. 한 문장으로

> 사내 위키(Confluence) 문서를 **내 컴퓨터에 모아두고**, 질문하면 **관련 문서를 찾아주는** 프로그램입니다. 인터넷·유료 AI 없이 동작합니다.

"MCP"는 **Model Context Protocol** — AI 비서(Claude 등)가 외부 도구를 호출하는 표준 규약입니다. GeryonMCP는 그 규약을 따르는 "검색 도구"라서, AI가 `search("휴가 규정")` 처럼 우리 시스템을 부를 수 있습니다.

---

## 1. 큰 그림 — 3단계

검색 엔진은 보통 이 세 단계로 나뉩니다. GeryonMCP도 똑같습니다.

```
①  수집(Acquire)        ②  적재(Ingest)              ③  검색(Search)
위키에서 문서를 받아     문서를 검색하기 좋게         질문을 받아
내 디스크에 저장   ──▶   가공해서 DB에 넣음    ──▶   관련 문서를 찾아 반환
(원본 그대로)            (쪼개고·숫자로 바꿔서)       (키워드 + 재정렬)
```

비유: **①장을 봐서 냉장고에 넣고(수집), ②재료를 손질해 정리하고(적재), ③주문이 오면 요리해 내놓는다(검색).**

이 3단계를 "**메달리온 아키텍처**"라는 이름으로 부르고, 각 단계의 데이터를 색으로 구분합니다:

| 이름 | 무엇 | 비유 | 어디에 |
|---|---|---|---|
| **Bronze** | 받은 원본 그대로 | 장 봐온 식재료 | 디스크 파일 `bronze/confluence/` |
| **Silver** | 검색용으로 가공한 것 | 손질해 정리한 재료 | SQLite DB `~/.geryon/geryon.db` |
| **Gold** | 사용자 맞춤 정보(동의어 등) | 내 입맛 메모 | `~/.geryon/gold/` |

> 왜 원본(Bronze)을 따로 두나? 가공물(Silver)은 언제든 원본에서 다시 만들 수 있어야 하기 때문입니다. DB가 깨져도 원본만 있으면 복구됩니다.

## 2. 검색이 왜 어려운가 (핵심 개념)

"휴가 규정"으로 검색한다고 합시다. 단순히 **"휴가"라는 글자가 든 문서**를 찾으면 될까요? 문제가 생깁니다:

1. 정답 문서 제목이 "**연차** 사용 안내"라면? → "휴가"라는 글자가 없어서 못 찾음. (**단어가 달라도 의미가 같은 문제**)
2. "휴가"가 든 문서가 500개라면? → 그중 **진짜 중요한 걸 위에 올려야** 함. (**순위 문제**)

이걸 풀려고 세 가지 기술을 씁니다:

### (a) 키워드 검색 — BM25 / FTS5
- **FTS5**: SQLite(파일 기반 DB)에 내장된 **전문 검색(full-text search)** 기능. "이 단어가 든 문서 빨리 찾기".
- **BM25**: 찾은 문서들에 **점수**를 매기는 공식. 흔한 단어(예: "그리고")는 낮게, 드문 핵심어는 높게 쳐줍니다.
- 빠르지만, 단어가 정확히 일치해야 잡습니다("휴가" ≠ "연차").

### (b) 의미 검색 — 임베딩 / 벡터
- **임베딩(embedding)**: 문장을 **숫자 목록(벡터)** 으로 바꾸는 것. 예: "휴가 규정" → `[0.12, -0.4, ...]`(384개 숫자). 의미가 비슷하면 숫자도 비슷해집니다.
- 그래서 "휴가"와 "연차"의 벡터가 가까워서, **단어가 달라도 의미로** 찾을 수 있습니다.
- 단점: 모든 문서 벡터와 거리를 재야 해서 **느립니다**(우리 DB는 11만 개 조각).

### (c) 재정렬 — Cross-encoder Rerank ★우리의 핵심
- 위 방법으로 후보 60개를 추린 뒤, **"질문과 이 문서가 정말 관련 있나?"** 를 한 쌍씩 정밀하게 다시 채점하는 작은 AI 모델입니다.
- 후보만 보므로(60개) 빠르고, **정답을 위로 끌어올리는 정확도가 가장 큽니다.**

> **GeryonMCP의 선택**: 약한 키워드를 무거운 벡터로 메우는 대신, **좋은 키워드(아래 설명) + 재정렬**로 갑니다. 이게 더 정확하고 가벼웠습니다(자세한 이유는 [`PERFORMANCE.md`](PERFORMANCE.md)).

> 참고: 한국어 키워드 검색에서 토크나이저(문장을 토막 내는 방식)가 중요합니다. 우리는 `trigram`(3글자씩 자름)에서 `porter unicode61`(단어 단위)로 바꿔 정확도가 크게 올랐습니다.

## 3. 데이터가 흐르는 길 (단계별 + 코드)

### ① 수집 — `src/geryon/acquire/confluence_atlassian.py`
- Confluence REST API를 호출해 페이지를 받아 `bronze/confluence/{공간}/{페이지ID}/` 에 저장합니다.
  - `content.html` (본문 원본), `meta.json` (제목·작성자·태그 등), `attachments/` (첨부)
- **멱등성**: 이미 받은 페이지는 버전을 비교해 **변경된 것만** 다시 받습니다(매번 전체를 안 받음).

### ② 적재 — `src/geryon/pipeline/ingest.py` (지휘자)
받은 파일을 검색용 DB로 가공합니다. 한 문서마다:
1. **정제** `normalize/normalizer.py` — HTML을 깔끔한 텍스트(Markdown)로 바꾸고, 제목·태그·문서유형(doc_type)을 뽑습니다.
2. **쪼개기 + 임베딩** `embed/embedder.py` — 본문을 ~512자 조각(**chunk**)으로 자르고, 각 조각을 임베딩(숫자 벡터)으로 변환합니다. 모델은 `intfloat/multilingual-e5-small`(로컬 ONNX).
3. **저장** `store/repository.py`(문서), `store/vector.py`(벡터), `store/db.py`(DB 스키마) — SQLite에 넣습니다. 넣을 때 **FTS5 색인**(키워드 검색용)이 자동으로 만들어집니다.
4. **부가 정보** `store/tree.py`(문서 계층), `pipeline/quality_signals.py`(문서 간 링크·중요도 점수)도 함께 계산해 둡니다.

> 핵심 원칙: **무거운 계산은 여기(적재 시)서 미리** 해둡니다. 검색은 빨라야 하니까요.

### ③ 검색 — 질문이 들어오면
가장 중요한 부분입니다. 진입점은 **`search/factory.py`의 `build_searcher()`** 하나입니다(서버·테스트·벤치가 모두 이걸 씁니다 — 길이 갈리면 측정이 거짓말을 하므로).

```
질문 "프로모션 마트 히스토리"
  │
  ▼  gold/search.py : GoldSearch
  ① 동의어 확장: "프로모션" → "프로모션 OR 할인율" 처럼 사전(Gold)으로 넓힘
  │
  ▼  search/hybrid.py : HybridRetriever
  ② 키워드로 후보 60개 추리기 (search/keyword.py, FTS5 BM25, 제목 가중)
  ③ 재정렬: search/rerank.py 의 cross-encoder가 (질문, 문서제목+태그) 쌍을
     정밀 채점해 순서를 다시 매김  ← 정확도의 핵심
  ④ 상위 k개 반환
  │
  ▼ (만약 재정렬 모델을 못 쓰면) 키워드+벡터 RRF로 자동 폴백(graceful fallback)
```

- **RRF(Reciprocal Rank Fusion)**: 두 검색(키워드·벡터) 결과 순위를 합치는 공식. 폴백 경로에서 씁니다.
- **graceful fallback**: 재정렬 모델이 없거나 실패해도 **죽지 않고** 옛 방식으로 결과를 냅니다.

최종적으로 `mcp/server.py`가 이 결과를 MCP `search` 도구의 응답으로 돌려줍니다.

## 4. 코드 지도 (`src/geryon/`)

| 폴더/파일 | 역할 | 비유 |
|---|---|---|
| `acquire/` | 위키에서 원본 수집 | 장보기 |
| `normalize/` | HTML→텍스트 정제, 유형 분류 | 재료 손질 |
| `embed/` | 문장→벡터 변환, 본문 쪼개기 | 재료를 숫자로 |
| `store/` | SQLite DB·FTS5·벡터·트리 저장/조회 | 냉장고 |
| `pipeline/` | 적재 전체 지휘 + 품질신호 계산 | 주방장(준비) |
| `search/factory.py` | **검색 조립 단일 진입점** | 주문 창구 |
| `search/keyword.py` | FTS5 BM25 키워드 검색 | 빠른 1차 탐색 |
| `search/rerank.py` | cross-encoder 재정렬(ONNX) | 정밀 심사 |
| `search/hybrid.py` | 후보→재정렬, 폴백 RRF | 요리 조립 |
| `gold/search.py` | 동의어 확장·개인화 | 손님 맞춤 |
| `search/query.py` | 질의→필터→검색→직렬화 공유 서비스(MCP·CLI 공용) | 공통 주문서 |
| `mcp/server.py` | MCP 도구(`search` 등 7종) 노출 | 서빙 |
| `cli.py` | 명령줄 도구(`geryon ...`, `geryon search` 포함) | 사장님 콘솔 |
| `config.py` | 설정값(모델·후보수·스레드 등) | 설정판 |
| `domain/models.py` | 데이터 모양 정의(Document·Chunk 등) | 그릇 규격 |

## 5. 검색 요청 하나가 거치는 길 (정리)

1. AI(또는 CLI)가 `search("질문", k=10)` 호출 → `mcp/server.py`
2. `build_searcher()`가 만든 `GoldSearch`가 받아 **동의어 확장**
3. `HybridRetriever`가 **키워드로 후보 60개** 추림(`keyword.py`)
4. `rerank.py`의 모델이 **후보를 정밀 재정렬**
5. 상위 10개를 **제목·URL·발췌**와 함께 반환
6. (모델 부재 시) 키워드+벡터 RRF로 폴백

## 6. 직접 해보기

```bash
# 1) 임베딩 모델 1회 내려받기(이후 오프라인)
geryon bootstrap

# 2) 원본(bronze/confluence)을 DB로 적재 — 시간이 좀 걸립니다
geryon reindex --source confluence --full

# 3) MCP 서버 실행 (AI가 이걸 호출)
geryon serve

# 상태 확인
geryon status     # 문서·청크 개수 등 JSON
geryon health     # 정상 여부
```

> 적재(2)를 하기 전에는 검색이 **0건**입니다. "설치 = 검색 가능"이 아니라 **적재가 필수 단계**입니다.

## 7. 용어집 (한 줄 정의)

- **MCP**: AI가 외부 도구를 부르는 표준 규약.
- **메달리온(Bronze/Silver/Gold)**: 원본/가공물/사용자맞춤 3계층.
- **FTS5**: SQLite 내장 전문검색 기능.
- **BM25**: 키워드 검색 점수 공식(드문 단어 우대).
- **임베딩/벡터**: 문장을 의미가 담긴 숫자 목록으로 변환한 것.
- **chunk**: 검색·임베딩을 위해 본문을 자른 조각(~512자).
- **cross-encoder rerank**: (질문, 문서) 쌍을 정밀 채점해 순위를 다시 매기는 모델.
- **RRF**: 여러 검색 결과 순위를 합치는 공식.
- **토크나이저**: 문장을 검색 단위로 토막 내는 방식(우리는 `porter unicode61`).
- **graceful fallback**: 일부가 실패해도 죽지 않고 대안으로 동작.
- **멱등성**: 같은 작업을 여러 번 해도 결과가 같음(수집을 다시 돌려도 안전).
