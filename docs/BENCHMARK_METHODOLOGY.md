# 검색 설정 벤치마크 방법론 — 통계적으로 검증 가능한 표준 절차

> "설정 A가 골든셋에서 더 잘 나왔다"는 **우연**일 수도, **골든셋 편향의 산물**일 수도, **진짜 효과**일
> 수도 있다. 이 문서는 셋을 기계적으로(사람의 수작업 검수 없이) 구분하는 표준 절차를 정리한다.

## 왜 필요한가 — 실제로 걸렸던 함정

`RERANK_POOL` 전수 스윕에서 `pool=20`이 기본값(`60`)보다 hit-rate가 훨씬 높게 나왔다.
언뜻 "pool을 줄여야 한다"는 결론처럼 보이지만, 원인이 두 가지로 갈릴 수 있었다:

1. **진짜 효과** — 작은 pool이 실제로 더 정확한 순위를 만든다.
2. **골든셋 편향** — 골든셋 질의가 `golden_bootstrap.py`로 "본문 희소어 조합"(예: `"항목수 대상수 코드"` 같은 형태)
   자동생성돼 자연어가 아니라 키워드 나열이고, 이런 질의엔 cross-encoder rerank가 오히려
   불리하게 작동해 rerank 관여도가 낮은 설정(pool 작음/rerank 끔)이 우연히 유리해 보일 수 있다.

**단순 hit-rate 비교(58% vs 76%)만으로는 이 둘을 구분할 수 없다.** 아래 두 기법을 조합해야 한다.

## 기법 1 — McNemar 검정 (통계적 유의성)

### 왜 이 검정인가
같은 골든셋의 **같은 케이스**에 설정 A/B를 각각 돌리면 결과가 **짝지어진(paired) 이진값**
(맞음/틀림)이 된다. 이런 "같은 표본, 두 방법, 이진 결과" 비교의 표준 통계기법이 McNemar 검정이다.
t-검정처럼 평균을 비교하는 게 아니라, **불일치 쌍만** 본다:

|            | B 맞음 | B 틀림 |
|------------|:---:|:---:|
| **A 맞음** | 둘다 맞음(무관) | A만 맞음 (b) |
| **A 틀림** | B만 맞음 (c) | 둘다 틀림(무관) |

- 둘 다 맞거나 둘 다 틀린 케이스는 **차이에 기여하지 않는다** — 버린다.
- `b`(A만 맞음) vs `c`(B만 맞음)의 비대칭이 우연(이항분포, p=0.5)에서 벗어나는지 정확이항검정으로 판정.
- `n = b + c`가 작으면(<25) 정확검정, 크면 카이제곱 근사를 쓰는 게 표준이나, 이 프로젝트 규모에선
  표준 라이브러리(`math.comb`)만으로 정확검정을 직접 구현해 scipy 의존 없이 계산한다.

### 실행
```bash
python scripts/ab_significance.py <cases.yml> <db> --a RERANK=1 --b RERANK=0
```
- `--a`/`--b`: `KEY=v,KEY2=v2` 형식(`GERYON_` 접두어 생략 가능), 내부적으로 `golden_eval.py`를
  설정별로 서브프로세스 실행(같은 프로세스에서 env만 바꾸면 반영 안 됨 — `config.py`가 import
  시점에 한 번만 읽기 때문).
- 출력: McNemar 분할표, p-value, `α=0.05` 기준 유의성 판정.
- **α=0.05, p<0.05 → "우연이 아니다"까지만 말해준다.** *"왜"* 그런지는 기법 2가 필요.

### 실측 결과 (참고)
| 비교 | 분할표(A만/B만) | p-value | 판정 |
|---|---|---|---|
| RERANK on vs off | 4 / 18 | 0.0043 | 유의함 |
| RERANK_POOL 60 vs 20 | 0 / 11 | 0.0010 | 유의함(POOL=20이 일방적 우위) |

## 기법 2 — Term-Density 스윕 (편향 대조군을 기계적으로 생성)

### 왜 필요한가
McNemar가 "유의하다"고 해도, 그 골든셋 **전체가 시스템적으로 편향**돼 있으면(예: 모든 케이스가
키워드 나열) 대조군이 없어 편향 여부를 검정할 수 없다. 사람이 질의를 "자연스럽게" 고쳐 검수하는
건 표준적이지만 수작업이다. **기계적** 대안: `golden_bootstrap.py --terms N`으로 질의의 키워드
밀도를 **코드로 통제**해 여러 골든셋을 만든다.

- `--terms 1` → 희소어 1개짜리 짧은 질의(자연어에 더 가까움)
- `--terms 5` → 희소어 5개 나열(더 키워드스러움)

### 로직
같은 비교(예: `RERANK=1` vs `RERANK=0`)를 term 밀도별 골든셋 각각에 McNemar로 돌린다.

- **효과가 진짜라면**: 밀도가 달라져도 승패 방향과 유의성이 **일관**돼야 한다.
- **골든셋 편향(키워드 편향)이라면**: 밀도가 낮아질수록(자연어에 가까워질수록) 효과 크기가
  **줄어들거나 역전**돼야 한다.

### 실행
```bash
for t in 1 2 3 4 5; do
  python scripts/golden_bootstrap.py <db> --out golden_terms$t.yml -n 60 --terms $t --seed 0
  python scripts/ab_significance.py golden_terms$t.yml <db> --a RERANK=1 --b RERANK=0
done
```
`--seed 0` 고정으로 재현 가능. `-n`(케이스 수)은 밀도 간 동일하게 유지해야 비교가 공정하다.

### ⚠️ 실패한 보조기법(교훈) — n_terms 내부 계층분석은 쓰지 마라
처음엔 "한 골든셋 안에서" 케이스별 희소어 수로 계층분석하면 되지 않을까 시도했다. 실패 이유:
`golden_bootstrap.py`가 **한 실행 안의 모든 케이스를 동일한 `--terms` 값으로 생성**하므로,
같은 파일 내 n_terms 분산이 **0**이라 대조군 자체가 없다. 이건 반드시 **여러 실행(파일)을
`--terms` 값을 바꿔가며** 만들어야 의미가 생긴다. (한 번 이 실수로 "편향 가설 약화"라는
잘못된 결론을 낸 적 있음 — 계층분석 결과를 볼 때 n_terms 분산이 실제로 있는지 먼저 확인할 것.)

## 표준 절차 (요약)

새 설정을 "채택해도 되는가" 판단할 때:

1. **베이스라인 골든셋**으로 `toolkit.py bench --sweep`으로 넓게 스캔 (`docs/PERFORMANCE.md` 참고).
2. 흥미로운(큰 차이 나는) 축이 나오면 → **McNemar**(`ab_significance.py`)로 우연인지 확정.
3. 유의하다면 → **term-density 스윕**(1~5)으로 같은 비교를 반복해 효과가 **일관**되는지 확인.
   - 일관됨 → 채택 근거로 인정.
   - term 낮을수록 효과 축소/역전 → 골든셋 편향 의심, **결론 보류**하고 진짜 자연어 질의
     (실사용 로그가 쌓이면 그것)로 재검증 필요.
4. `RERANK_QUANTIZE`/`RELEVANCE_DISTANCE`/`RERANK_VEC_POOL`처럼 **한 축에서 차이가 아예 없으면**
   (예: 35/60 = 35/60) McNemar 자체가 무의미(`b=c=0`) — 이미 무해함이 증명된 것이므로 이 절차
   생략하고 기본값 유지.

## 완결 사례 — RERANK on/off, term-density 1~5 스윕 (2026-08-24)

`RERANK=1`(기본, cross-encoder 켬) vs `RERANK=0`(끔)을 term-density 1~5 각각(n=60)에서 McNemar:

| terms | A(on)만 맞음 | B(off)만 맞음 | p-value |
|:---:|:---:|:---:|:---:|
| 1(가장 자연어에 가까움) | 0 | 11 | 0.0010 |
| 2 | 5 | 18 | 0.0106 |
| 3 | 4 | 18 | 0.0043 |
| 4 | 6 | 21 | 0.0059 |
| 5(가장 키워드나열) | 3 | 21 | 0.0003 |

**판정**: 키워드 편향 가설이 맞다면 terms=1에서 효과가 사라지거나 줄어야 하는데, 오히려
terms=1에서 가장 깨끗하게(11:0, 완전 일방향) 나왔다 — **밀도가 낮아져도 효과가 줄지 않고
유지**되므로, 위 절차 3단계 기준("일관됨 → 채택 근거로 인정")에 따라 **골든셋 편향이 아니라
진짜 효과일 가능성이 높다**로 결론.

→ **시사점**: 현재 cross-encoder rerank 단계가 이 코퍼스에서 순수 하이브리드(FTS5+벡터 RRF)
보다 오히려 검색 품질을 낮추고 있을 가능성. 프로덕션 반영 전 최종 확인 필요(아래 한계 참고).

`RERANK_POOL`(60 vs 20)은 이 스윕을 아직 안 돌림 — 같은 방식으로 재현 가능.

### 소표본 경보 — 검정이 성급한 결론을 막은 실례

LLM 골든셋 6건으로 `RERANK_POOL` 60 vs 20 을 비교했을 때:

- `bench` 결과만 보면: **양쪽 다 hit 4/6 인데 pool 20 이 1.5배 빠름** → "pool 20 채택" 결론이 나온다.
- `ab_significance` 결과: 분할표가 `A만 맞음 0 / B만 맞음 0`(불일치 쌍 자체가 없음) →
  **p=1.0000, 유의하지 않음**. 도구가 *"n=6 으로는 우연과 구분 불가, n≥100~200 권장"* 을 경고.

**hit-rate 가 같다는 것과 성능이 같다는 것은 다르다.** 표본이 작으면 두 설정이 정확히 같은
케이스를 맞히고 틀려서 비교 정보량이 0이 될 수 있다. `bench` 만 보고 결론 내지 말 것.
(속도 차이는 별개 축이므로 `profile_resources` 로 따로 판단한다.)

## 기법 3 — LLM 골든 생성 (룰기반의 질의 스타일 편향 보완)

### 왜 필요한가
기법 2(term-density)는 **키워드 밀도**를 바꿔 편향을 검사하지만, `golden_bootstrap.py` 가 만드는
질의는 밀도와 무관하게 전부 **희소어 나열**(`"진입수 구매고객수 bp"`)이다. 실사용 질의는
문장형인데 테스트셋이 키워드형이면, 문장 관련성을 학습한 cross-encoder rerank 가 구조적으로
불리해진다. `golden_llm.py` 는 같은 문서에서 **자연어 질문**을 역생성해 이 축을 보완한다.

```
룰기반 : "진입수 구매고객수 bp"
LLM   : "쿠폰 관리 화면에서 할인 코드를 등록하려면 어떤 단계를 거쳐야 하나요?"
```

### 사용법
```bash
# 기본 — 문서 20건 × 문서당 2질문, 자동 검증 통과분만 초안에 수록
python scripts/golden_llm.py <db> --out golden_llm.draft.yml -n 20 --per-doc 2

# 현 검색기가 정답을 top_k 에 넣는지 표기까지(탈락시키지 않음, 검수 참고용)
python scripts/golden_llm.py <db> --out golden_llm.draft.yml -n 20 --verify

# 모델 지정(기본 GERYON_LLM_MODEL, 없으면 qwen3.5:latest)
GERYON_LLM_MODEL="<ollama 모델명>" python scripts/golden_llm.py <db> ...
```

| 옵션 | 뜻 |
|---|---|
| `-n` / `--per-doc` | 대상 문서 수 / 문서당 질문 수 |
| `--body-chars` | LLM 에 넣을 본문 길이(기본 1500) — 길수록 품질↑·속도↓ |
| `--min-body` | 너무 짧은 문서 제외(기본 300자) |
| `--seed` | 문서 샘플링 고정(질문 생성 자체는 비결정적) |
| `--verify` | `_self_check` 표기 추가 |

로컬 **Ollama** 만 호출한다(외부 API 없음). 오프라인 원칙은 유지된다.

### 자동 검증 — LLM 산출물을 그대로 믿지 않는다
생성 즉시 아래를 적용하고, **통과한 것만** 초안에 넣는다. 탈락 사유는 실행 끝에 집계된다.

| 검증 | 목적 | 탈락 조건 |
|---|---|---|
| **앵커** | **할루시네이션 차단** | 질문의 핵심어가 원문 본문에 하나도 없으면 탈락 |
| **자기참조 금지** | 검색이 아니라 문자열 매칭이 되는 것 방지 | 질문 토큰의 80% 이상이 정답 제목에 포함되면 탈락 |
| **길이** | 실사용 질의 범위 | 4자 미만 / 60자 초과 |
| **중복** | 같은 문서에서 유사 질문 반복 방지 | 자카드 0.6 초과 |
| **마크다운 정제** | 실사용 질의엔 없는 문자 제거 | `**강조**` 등 자동 제거(탈락 아님) |

**`_self_check`(현 검색기가 맞히는지)는 탈락 기준이 아니다.** MISS 를 버리면 "지금 검색기가
이미 맞히는 문제"만 남아 골든셋이 개선 측정 능력을 잃는다 — 표기만 하고 판단은 사람이 한다.

### 룰기반 vs LLM — 어느 쪽을 쓰나
둘 중 하나가 아니라 **둘 다** 쓰고, 결론이 양쪽에서 일치하는지 본다.

| | `golden_bootstrap.py` (룰) | `golden_llm.py` (LLM) |
|---|---|---|
| 결정성 | ✅ 시드 고정 시 완전 재현 | ❌ 비결정적(모델·temperature) |
| 오프라인 | ✅ 완전 무LLM | △ 로컬 Ollama 필요 |
| 속도 | 빠름(수천 건 가능) | 느림(문서당 수 초) |
| 질의 성격 | 키워드 나열 | 자연어 문장 |
| 할루시네이션 | 없음(원문 토큰만 사용) | 있음 → 앵커 검증으로 차단 |

**판정 규칙**: 설정 A/B 비교 결론이 **룰기반과 LLM 골든셋 양쪽에서 같은 방향**이면 채택 근거로
인정한다. 한쪽에서만 나타나면 그 골든셋의 질의 스타일에 기인한 것일 수 있으므로 보류한다.

```bash
# 같은 비교를 두 골든셋에서 각각 검정 — 방향이 일치하는지 확인
python scripts/ab_significance.py golden_rule.yml <db> --a RERANK=1 --b RERANK=0
python scripts/ab_significance.py golden_llm.yml  <db> --a RERANK=1 --b RERANK=0
```

### 커밋 전 필수
LLM 생성물은 **비결정적**이므로 `tests/golden/` 에 확정하기 전 사람이 검수한다:
질문이 자연스러운지 · 정답이 그 문서로 유일한지 · 사내 고유명이 질의에 노출되지 않는지
(마지막 항목은 공개 저장소 기준 — `CLAUDE.md` 체크리스트 참고).
`_meta.generator` 에 사용 모델이 기록되므로 재현 시 같은 모델을 쓸 것.

## 알려진 한계
- 골든셋이 `golden_bootstrap.py` 자동생성(반자동, 사람 검수 전) 기준이라, **모든 term-density
  변형이 여전히 "희소어 기반 합성 질의"**라는 근본 성격은 못 벗어난다. 완전한 검증은 결국
  **실사용 질의 로그** 확보 후 그걸로 골든셋을 재구성하는 것 — 이 절차는 그 전까지의 최선.
- McNemar는 **표본 내** 우연성만 검정한다. 표본(n=60) 자체가 코퍼스를 대표하지 않으면
  결과도 대표성이 없다 — 케이스 수를 늘릴수록(`-n`) 신뢰도가 오른다.
