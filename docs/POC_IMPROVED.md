문서 처리 접근법(단일 프롬프트 / Map-Reduce 병렬 / 슬라이딩 윈도우)을
동일한 입력 문서 3종에 대해 실행하고, 소요 시간·세그먼트 수·액션아이템 수·
오류 유형을 정량 비교한 PoC 결과입니다. 실제 입력 내용은 모두 제거하고
방법론과 측정값만 남겼습니다.

## 주요 발견사항

### B' Map-Reduce 병렬화
- **속도 개선 성공**: 원시 전사체 1052초 → 372초 (2.8배 단축)
- **품질 저하**: 라벨링 1회 → 세그먼트 결합 중 이질적 그룹(잡담성 발화 + 기술 논의)이 함께 묶임
- **구조화 문서 부적합**: 텍스트 단락을 topic/peripheral/procedural로 기계적 분류 (Phase 1 = procedural 등 엉뚱한 라벨)
- **결론**: 속도 개선은 실증됐으나 A보다 품질이 낮음. 긴 문서(10,000자+)에서 재평가 필요

### C' 슬라이딩 윈도우
- **세그먼트 폭발**: 21블록 → dedup 후 22개 (A의 2.75배), 동일 기술 안건이 5개로 중복 생성
- **dedup 한계**: 제목 키워드 60% 겹침 기준으로는 내용이 다른 중복을 충분히 제거하지 못함
- **논문 조건과 괴리**: MS Research arXiv:2307.15793은 수천 발화 규모의 긴 회의 대상 — 짧은 발화 21개짜리 회의엔 윈도우 설정이 무의미
- **결론**: 30분 이상 긴 회의(100블록+) 문서에서 재평가 필요. 현재 테스트 데이터엔 부적합

## 최종 결론

**방식 A (단일 프롬프트)가 현재 데이터 규모에서 최선**:
- 속도 최상 (48~73초)
- 품질 최상 (3스트림 자연 분리, 세그먼트 과분할 없음)
- 논문 기반 방식들은 수천 발화 대규모 회의에 설계된 것 → 현재 30분 내외 회의(21블록)에는 오버스펙

**개선 방향 재정립**:
- 방식 B' 병렬화: **큰 문서(50블록+) 전용**으로 조건부 채택
- 방식 C' 슬라이딩: **100블록+ 긴 회의 전용** (또는 포기)
- 현재 프로덕션 후보: **방식 A** → `src/geryon/analyze/llm_extract.py` 구현

## 문서 1 — 구조화 회의록 (요약본)

- 3,952자 / 블록 0개
- 특성: 사람이 정리한 요약형 회의록. 문단 단위 구조가 명확하고 발화 경계가 없음.

### 방식 A — 단일 프롬프트 (베이스라인)
- 소요: **73.2초**
- topic 2 / peripheral 1 / procedural 1 / 액션 3개
- 관찰: 기술 안건 2건과 잡담성 안건·절차 안건을 각각 별도 스트림으로 자연스럽게 분리.
  담당자별 액션아이템이 개별 topic에 정확히 귀속됨.

### 방식 B' — Map-Reduce + 병렬 요약
- 소요: **602.1초**
- topic 1 / peripheral 0 / procedural 0 / 액션 2개
- 관찰: 이질적 안건이 단일 topic으로 병합되어 스트림 분리 실패.
  구조화 문서에서는 병렬 축약이 오히려 정보를 뭉갬.

### 방식 C' — 슬라이딩 윈도우 (10블록+3스트라이드)
- 소요: **92.0초**
- topic 2 / peripheral 1 / procedural 1 / 액션 4개

  액션아이템이 소폭 과다 추출됨.

## 문서 2 — 원시 회의 전사체 (임의 확장)

- 3,413자 / 블록 21개
- 특성: 발화 단위로 분절된 원시 전사체. 기술 논의와 잡담이 섞여 있음.

### 방식 A — 단일 프롬프트 (베이스라인)
- 소요: **53.2초**
- topic 6 / peripheral 1 / procedural 1 / 액션 7개
- 관찰: 6개 기술 안건을 명확히 분리하고, 잡담성 발화는 peripheral,

### 방식 B' — Map-Reduce + 병렬 요약
- 소요: **371.6초** (기존 1052초 대비 2.8배 단축)
- topic 3 / peripheral 3 / procedural 0 / 액션 8개

### 방식 C' — 슬라이딩 윈도우 (10블록+3스트라이드)

  dedup 후에도 중복 제거가 불완전. 짧은 회의에 윈도우 방식은 명백히 오버스펙.

## 부록 — 방법론 정의

- **방식 A (단일 프롬프트)**: 문서 전체를 한 번의 프롬프트로 처리하여
  topic / peripheral / procedural 3스트림과 액션아이템을 추출.
- **방식 B' (Map-Reduce + 병렬)**: 문서를 청크로 나눠 각 청크를 병렬 요약(Map)한 뒤
  결합(Reduce)하여 세그먼트를 구성. 축약 단계를 병렬화해 속도를 확보.
- **방식 C' (슬라이딩 윈도우)**: 10블록 윈도우 · 3블록 스트라이드로 겹쳐 훑으며
  세그먼트를 추출하고 제목 키워드 겹침 기준으로 dedup.

측정 지표: 소요 시간(초), 세그먼트 수(seg), 스트림별 세그먼트 수
(topic/peripheral/procedural), 액션아이템 수, 빈응답·타임아웃·과분할 등 오류 유형.
