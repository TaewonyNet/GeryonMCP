# 문서 정제 레이어 리서치 — GeryonMCP v2

> **목적:** 회의 전사체·대량 비정형 문서를 검색 가능한 단위로 정제하는 방향 탐색
> **상태:** PoC 완료 → 프로덕션 설계 확정

---

## 1. 배경 — 왜 지금인가

### GeryonMCP 현재 포지션

GeryonMCP는 Confluence·Jira·Bitbucket·Git 등 여러 소스를 단일 인터페이스로 묶는 로컬 AI 검색 서버다.
MCP 프로토콜을 통해 LLM 세션 안에서 바로 조직 내부 문서를 조회할 수 있다.

### 관리형 검색 도구(예: SaaS AI 검색)와 비교

| 항목 | 관리형 SaaS 검색 | GeryonMCP |
|------|------|-----------|
| 최신성 | 실시간 | sync 기준 |
| 커넥터 수 | 다수(다양한 외부 SaaS 연동) | Confluence, Jira, Bitbucket, Git |
| 이슈 액션 | 이슈 생성·할당 가능 | 검색 전용 |
| 데이터 처리 | 클라우드 전송(LLM 제공사 포함) | 완전 로컬·폐쇄망 가능 |
| 비용 | 유료 구독 필수 | 로컬 실행만 |
| 요청 제한 | 사용량 상한 존재 | 없음 |
| 회의 전사체 | 불가(외부 데이터) | 커스텀 소스 추가 가능 |

**핵심 결론:** 일반 위키·이슈 검색은 관리형 SaaS 도구가 우위. GeryonMCP가 의미를 갖는 구간은
1. 폐쇄망·데이터 보안 요건(기밀 문서를 외부 AI에 보낼 수 없는 환경)
2. 관리형 도구가 아예 접근 불가한 데이터(회의 전사체, 로컬 대량 문서)

## 2. 문제 정의

### 2-1. 현재 "검색 불가 영역"

```
위키/이슈/코드 저장소          → GeryonMCP 인덱싱 ✅
회의 전사체                    → 인덱싱 없음 ❌
구두 결정·합의                 → 어디에도 없음 ❌
대량 내부 문서 (PDF, Excel)    → 인덱싱 없음 ❌
채팅 메시지                    → 인덱싱 없음 ❌
```

사용자가 실제로 찾는 것:

- "저번 주 회의에서 누가 이 작업을 하기로 했지?"
- "특정 배포 결정이 언제 났지?"
- "이 항목을 담당자에게 확인하기로 한 게 누구야?"

→ 위키에도 없고, 이슈에도 없고, 관리형 검색 도구도 못 찾는다.
→ 결국 사람에게 물어본다(채팅 DM, 구두).

### 2-2. 왜 단순 저장으로는 안 되는가

원시 전사체를 그대로 body_markdown에 저장하면:

```
snippet: "화자A: 네 지난주이제화자B: 어 저는화자B: 잠깐 이번 안건..."
```

- 화자 라벨이 단어 중간에 삽입됨(자동 화자분리(diarization) 깨짐)
- 구어 비유창성, 맥락 없는 단편 발화
- 특정 결정 사항이 수만 자 전사체 어딘가에 묻혀 검색 불가
- 임베딩 기반 클러스터링도 구어체 텍스트에서 신호 약함(검증 완료)

**결론: 원시 전사체 → 검색 가능한 단위로 정제하는 레이어가 필요하다.**

## 3. AS-IS — 현재 GeryonMCP 처리 흐름

```
외부 소스 (위키 등)
    ↓ acquire (원본 수집)
    ↓ ingest (markdown 변환 + 임베딩)
    ↓ SQLite DB (documents 테이블)
    ↓ search() → hits (snippet + score)
    ↓ get_document() → 전체 body_markdown
```

**문서 단위:** 페이지 1개 = Document 1개. 본문 전체가 body_markdown에 저장.

**현재 검색 출력 예시:**
```json
{
  "doc_id": "confluence:0000000000",
  "title": "예시 문서 제목",
  "snippet": "## 개요\n특정 업무 스펙 문서의 데이터 처리 흐름을...",
  "score": 0.46
}
```

**한계:**
- 회의 전사체: 인덱싱 경로 없음
- 대량 문서: 전체가 하나의 document → 특정 섹션 검색 정확도 낮음
- 구조화 정보(결정사항, 액션아이템) 추출 없음

## 4. TO-BE — 문서 정제 레이어

### 4-1. 핵심 원칙

> **정제 = 검색 가능한 의미 단위로 분해 + 구조화 메타데이터 추가**

단순 요약이 아님. 원문을 버리지 않고 "검색되어야 하는 단위"로 재편성.

### 4-2. 문서 유형별 정제 전략

#### 회의 전사체

**문제:** 구어, 깨진 화자 라벨, 수만 자, 잡담·결정·절차 혼재
**정제 방법:** LLM 3스트림 분리

| 스트림 | 내용 | 검색 가치 |
|--------|------|-----------|
| `topic` | 공식 안건, 기술 논의, 명시적 결정 | 높음 |
| `peripheral` | 잡담처럼 보이나 결정·정보 포함 가능 | 중간(결정 있으면 높음) |
| `procedural` | 화면 공유 요청, 일정 조율, 마이크 잡음 | 낮음(보존은 함) |

각 스트림 세그먼트 → 별도 Document로 저장:
```
doc_id: meeting:YYYY-MM-DD:seg_05
title:  [★결정] 특정 안건 확인
body_markdown: |
  ## 요약
  특정 예산/수치 항목 확인 필요.
  담당자에게 확인 후 공지 예정.

  ## 원문 근거
  화자A: 잠깐, 이 안건 얘기 잠깐 해도 돼요? 수치가 얼마예요?
  ...
  화자B: 일단 담당자한테 확인하고 다시 얘기해요.

raw_meta:
  stream: peripheral
  contains_decision: true
  action_items:
    - owner: 화자A
      description: 담당자에게 확인 후 공지
      due: 이번 주
```

**검색 결과 변화:**
```
AS-IS: "특정 안건" 검색 → 결과 없음
TO-BE: "특정 안건" 검색 → [★결정] 특정 안건 확인 (YYYY-MM-DD 회의)
```

#### 대량 구조화 문서 (PDF, 긴 위키 페이지)

**문제:** 페이지 1개 = Document 1개면 긴 문서의 특정 섹션 검색 부정확
**정제 방법:** 섹션 단위 청킹 → 각 섹션을 sub-document로 저장

```
원본: "연간 전략 기획서" (80페이지)
↓
섹션 1: "1Q 목표"  → Document
섹션 2: "2Q 목표"  → Document
...
```

### 4-3. 저장 구조

기존 `documents` 테이블 스키마 그대로 활용. 별도 `meetings.db` 파일:

```sql
-- 기존 스키마 그대로, doc_type 필드로 구분
doc_type = "meeting_segment"   -- 회의 세그먼트
doc_type = "doc_section"       -- 문서 섹션

-- raw_meta JSON에 추가 구조화 정보
raw_meta = {
  "stream": "peripheral",
  "contains_decision": true,
  "parent_doc_id": "confluence:0000000000",
  "action_items": [...],
  "linked_topic": "관련 안건 식별자"
}
```

`GERYON_DB=main.db,meetings.db` 설정만으로 기존 페더레이션 검색에 자동 편입. **server.py 수정 없음.**

### 4-4. 처리 파이프라인

```
원시 전사체 / 대량 문서 입력
    ↓
[전처리] 화자 라벨 정규화, 타임스탬프 분절
    ↓
[임베딩 청킹] 의미 단위 경계 탐지 (core.py 활용)
    ↓
[LLM 추출] 로컬 LLM → 3스트림 분리 + 구조화
    ↓
[검증] evidence fuzzy match (원문 포함 여부 확인)
    ↓
[저장] meetings.db → documents 테이블
    ↓
[검색] 기존 GeryonMCP search() 자동 편입
```

## 6. 인프라 요구사항 — 로컬 LLM 실행

> PoC 기준: 로컬 LLM(약 9.7B, Q4_K_M 양자화), Ollama, `num_ctx=32768`, `num_predict=16384`

### 처리 용량

| 설정 | 입력 가용 토큰 | 처리 가능 분량 | 회의 길이 기준 |
|------|:-:|:-:|:-:|
| `num_ctx=32768` (현재) | ~16K 토큰 | ~12,000자 | **최대 1시간** |
| `num_ctx=65536` | ~48K 토큰 | ~36,000자 | 최대 3시간 |
| `num_ctx=131072` | ~112K 토큰 | ~84,000자 | 최대 8시간 |

- 1시간 회의 전사체 기준: **~8,000~12,000자**(구어, 타임스탬프 포함)
- 출력 예약(16K)을 빼면 현재 32K 설정으로 **1시간 회의는 여유롭게 처리 가능**
- 2시간 이상이면 `num_ctx=65536` 권장(VRAM 7.3GB)

### VRAM 요구량

| GPU VRAM | 실행 가능 여부 | 최대 처리 분량 |
|------|:-:|:-:|
| **8GB** | ✅ (권장 최소) | ~42,000자 (~4시간) |
| 12GB | ✅ | ~129,000자 (~12시간) |
| 16GB | ✅ | ~217,000자 이상 |
| CPU 전용 | △ 가능하나 매우 느림 | 동일 |

**산출 근거:**
- 모델 가중치 (Q4_K_M): ~5.1 GB
- KV 캐시 32K: ~1.1 GB → 합계 **~6.2 GB**
- KV 캐시 64K: ~2.2 GB → 합계 **~7.3 GB**
- 8GB GPU = `num_ctx=65536` 까지 실행 가능(2~3시간 회의 커버)

### 처리 속도 (PoC 실측, 단일 프롬프트 방식)

| 문서 크기 | 처리 시간 |
|--|:-:|
| ~3,000자 (30분 회의) | 48~73초 |
| ~6,000자 (예상 1시간) | ~120~150초 |
| ~12,000자 (예상 2시간) | ~250~300초 |

- GPU 성능에 따라 2~5배 차이 가능
- 배치 처리(여러 회의록 순차)는 병렬 불필요 — 1개씩 처리로 충분

### DB 적재 산출물

1시간 회의(~10,000자) 처리 시 meetings.db에 저장되는 레코드:

| 항목 | 수량 |
|--|:-:|
| topic 세그먼트 | 5~8개 |
| peripheral 세그먼트 | 1~3개 |
| procedural 세그먼트 | 0~2개 |
| 액션아이템 (전체 합) | 5~12개 |
| **총 Document 레코드** | **8~15개** |

각 Document(= 세그먼트):
```json
{
  "doc_id": "meeting:YYYY-MM-DD:seg_03",
  "title": "[★결정] 특정 기술 성능 테스트",
  "body_markdown": "## 요약\n화자A: 특정 저장소 적재에 시간이 오래 걸림... 대안 기술 테스트하기로.\n\n## 근거\n화자A: 적재 얘기 좀 하면, 처리에 시간이 오래 걸려서...",
  "raw_meta": {
    "stream": "topic",
    "contains_decision": true,
    "linked_topic": null,
    "action_items": [
      {"description": "대안 기술 성능 테스트 및 결과 공유", "owner": "화자A", "due": "테스트 완료 시"}
    ]
  }
}
```

## 7. 열린 문제

- [ ] **증분 처리:** 같은 전사체 재처리 방지 (content_hash 기반)
- [ ] **2시간+ 회의:** `num_ctx=65536` 으로 증설 (8GB GPU 이상 필요, 설정 1줄 변경)
- [ ] **evidence 검증:** LLM 할루시네이션 방지 (fuzzy match 임계값 튜닝)
- [ ] **owner 정규화:** 동일 인물의 여러 표기(영문/한글) → 개인별 분리
- [ ] **교차문서 주제 추적:** 동일 안건이 여러 회의에 반복될 때 연결
- [ ] **채팅 통합:** 채팅 합의도 같은 파이프라인으로 처리 가능한지
- [ ] **배치 처리:** 아카이브된 회의록 일괄 처리
